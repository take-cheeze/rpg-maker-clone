- The **WebAssembly CMake configure** no longer re-probes the Emscripten
  toolchain on every build: it dropped from **110s to 7s**. Almost all of that
  time was 62 nested `try_compile` projects — every `check_include_file_cxx` /
  `check_cxx_symbol_exists` / `check_c_compiler_flag` in ng-log, gflags, quickjs
  and lvgl runs a full `emcc` invocation (python driver, clang, wasm-ld) at
  ~1.7s each, against the sub-100ms `cc` the native build pays. The answers are
  fixed properties of the Emscripten sysroot, so `cmake/emscripten-probe-cache.cmake`
  seeds them and the `check_*` macros skip the probes outright. Verified against
  a real Emscripten 5.0.6 configure: all 65 probe results and ng-log's generated
  `config.h` are byte-identical, and `build.ninja` differs only in which files
  trigger a reconfigure. The file is generated by
  `scripts/gen_emscripten_probe_cache.rb` and gated on the Emscripten version,
  so a toolchain bump falls back to probing normally (with a `STATUS` message
  asking for a regeneration) rather than silently reusing stale answers.
