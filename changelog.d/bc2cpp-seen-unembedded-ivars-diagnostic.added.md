bc2cpp: report the ivars examined but not embedded, so the gap is answerable

`IvarLayout.analyze` returns only the EMBEDDABLE subset, so an ivar that stayed
UNKNOWN is absent from its result and indistinguishable from one never analysed.
"How many more ivars are embeddable?" therefore had no answer without
instrumenting the fixed point and reading one pass as if it were the settled
result -- which is what four wrong numbers in a row came from.

`BC2CPP_SEEN_IVARS=1` prints one `SEEN_UNEMBEDDED Owner#@ivar (type)` line for
every ivar the sweep examined and did not embed, read from the FINAL table, not
from inside the loop. The return value is unchanged and the flag is off by
default, so no caller and no generated byte can depend on it.

With it, the real accounting on the hot-only wio closed world (full compilation,
core mrblib, BC2CPP_NO_ONLY_OWNERS=1):

    EMBED (embedded now)                        281
    SEEN_UNEMBEDDED (examined, not embedded)     705
      :unknown    -> the write is unreadable     568
      :nil_literal -> known, but no storage        137
    total ivars the analysis has an opinion on  986

so 496 `:unknown` ivars sit on a WIRED embedding owner -- the set that would
become embeddable if their writes were readable, led by RPG2k::Scene::Map (116),
Game::Interpreter (43), Game::Actor (25), Game::State (21), RPG2k::Window (20).
That is the number the earlier instrumentation could not produce.

The 137 `:nil_literal` ones are already KNOWN and deliberately not embeddable:
C_TYPE has no entry for nil, so they stay in iv_tbl (NILABLE_EMBED_SUPPORT).
They are listed so the two cases are not conflated -- an unreadable write and a
missing storage representation are different problems with different fixes.

Verified output-neutral: with the flag off, the generated C++ is byte-identical
(object .text 3,940,130, BUILD OK) and scripts/bc2cpp_*_check.rb is 46 pass /
5 fail, the same 5 that fail at the commit this branch started from.
