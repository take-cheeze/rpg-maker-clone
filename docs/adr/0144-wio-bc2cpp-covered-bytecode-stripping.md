# 144. Strip the interpreted bytecode of bc2cpp-covered methods on wio

Date: 2026-09-12

## Status

Accepted

## Context

docs/adr/0139 (and its many follow-ups) built `tools/bc2cpp/bc2cpp.rb`, a
whole-program mruby-bytecode-to-C++ AOT compiler that now covers 1,573
methods across three gems (`mruby-lcf-compiled`, `mruby-rgss-compiled`,
`mruby-rpg2k-compiled`, opt-in via `RPGMAKER_BC2CPP=1`). docs/adr/0142/0143
measured its real, linked cost on the actual Wio Terminal
(`wio_rgss_boot` firmware) and found it a clear net loss: **+1,067,524
bytes of real flash, zero RAM change**, on a board already 675,960 bytes
over its 507,904-byte budget without it.

The root cause, identified in 0143 and confirmed again here: bc2cpp never
removes the ORIGINAL interpreted bytecode for a method it AOT-compiles.
`mrb_define_method` at the `*-compiled` gem's own `gem_init` overwrites the
class's method-table entry with the C++ override, but the original
bytecode is still fully compiled into flash by `mrbc` — mruby loads each
gem's entire mrblib as one monolithic byte array via a single
`mrb_load_irep_buf` call, so individual methods inside it are not separable
linker sections a plain `--gc-sections` dead-strip could ever remove. Every
already-covered method's flash cost is paid twice: once as a bytecode blob,
once as compiled C++.

This project already has a proven mechanism for exactly this shape of
problem: `strip_wio_inline_helpers.rb` / `strip_wio_debug_output.rb` are
wio-only, build-time source rewriters (`build_config.rb`'s
`wio_strip_inline_helpers`/`wio_strip_debug_rbfiles`) that rewrite a
build-time copy of a gem's `.rb` files before `mrbc` ever sees them,
**never** touching the checked-in source — real CRuby-based regression
scripts (`scripts/rpg2k_render_check.rb` and friends) call many of the same
methods directly by name for genuine test coverage that has nothing to do
with wio, so the checked-in definitions have to survive untouched on every
other target. This ADR generalizes that mechanism to bc2cpp's own real
coverage.

## Decision

Built a new, general, wio-only build step —
`wio_strip_bc2cpp_stubs(spec, compiled_gem:, owners:)` in `build_config.rb`,
backed by two new scripts — that deletes the whole `def ... end` (header,
body and `end`, nothing left in its place) of every method a `*-compiled`
gem's own real bc2cpp.rb run registers a C++ override for, out of a
build-time copy of the *base* gem's mrblib. (An earlier version of this
mechanism kept the `def` and replaced only its body with a `raise
NotImplementedError` stub; a real measurement found outright deletion
smaller still — see "What was measured" for the full history of both
designs.) It is wired into `mruby-rgss/mrbgem.rake` for a single,
deliberately bounded proof set:
**all 17 of `RGSS::Sprite`'s real, bc2cpp-registered methods** — not
`mruby-rgss-compiled`'s own full 14-owner list, and not any other gem's
owners. Per this ADR series' own established discipline (see 0139's own
"prove it on a bounded subset first" precedent for `.singleton` support
and every prior bc2cpp round), scope was deliberately kept small enough to
verify completely rather than swept broadly and trusted.

### The two new pieces

**`tools/bc2cpp/wio_registered_methods.rb`** — answers "what did this
`*-compiled` gem's own real build actually register a C++ override for,"
without ever re-deriving that answer independently. It runs the *exact
same* `bc2cpp.rb` invocation that gem's own `mrbgem.rake` performs (same
`ONLY_OWNERS`/`OTHER_OWNERS`/`NATIVE_SRCS`/closed-world source set, built
from the very same `compiled_gems.rb` helpers —
`BC2CPP_COMPILED_GEMS`/`closed_world_mrblib_srcs`/`core_native_srcs`/
`external_gem_native_srcs` — that `mrbgem.rake` itself calls, `require`d
rather than re-typed), then parses ONLY bc2cpp.rb's own real,
already-trustworthy `== compiled entry points ==` stderr diagnostic into a
TSV: `owner<TAB>name<TAB>arity<TAB>visibility<TAB>singleton(0|1)`. A hand-
copied `owners:` array would only give the *candidate* class list, not the
real, final per-method registration (which methods on that class actually
compiled, their real arity/visibility, whether one is secretly a
`.singleton` pseudo-owner) — only bc2cpp.rb's own diagnostic, generated by
really walking the bytecode, can answer that, and this script's whole
reason to exist is never guessing it independently.

**`strip_wio_bc2cpp_stubs.rb`** — the AST-based rewriter, structurally the
generalized sibling of `strip_wio_inline_helpers.rb`. Given the TSV above
and an owner allowlist, it parses the target `.rb` file with
`RubyVM::AbstractSyntaxTree`, walks real `CLASS`/`MODULE` nesting to
recover each method's real owner path (e.g. `RGSS::Sprite`), and for every
`DEFN` node whose `(owner, name)` matches a registered entry, **deletes**
every line from the method's own header through its own `end` (both real
AST-derived line spans, `first_lineno`/`last_lineno` — never a text
search) outright — no replacement text of any kind:

```ruby
# before (mruby-rgss/mrblib/lib.rb, checked-in source, untouched):
def width
  bitmap ? bitmap.width : 0
end

# after (build-time-only copy fed to mrbc):
#
# (nothing -- the whole def is gone)
```

This went through two earlier designs before landing here, both replaced
by a real measurement rather than an argument:

1. **First**: keep the `def`, replace the body with `raise
   NotImplementedError, "#{self.class}#width: interpreted bytecode
   stripped for wio -- ..."` (a descriptive message). A real link
   **regressed** flash with this in place (see "Two stub designs a real
   measurement rejected" below) — a per-method string literal is never
   shared across separate compiled methods' own `POOL` sections, so 17
   distinct message strings cost more than the 17 trivial one-liners they
   replaced.
2. **Second**: keep the `def`, replace the body with a bare `raise
   NotImplementedError` (no message) — cheaper than (1), and what this
   ADR originally shipped with a measured **-512 byte** real, linked
   recovery.
3. **Current, shipped design**: delete the `def` entirely — header, body
   and `end`, nothing left in its place. Once a `*-compiled` gem's own
   `gem_init` installs the real C++ override, `respond_to?`/`.arity`/
   `method(:x)` all answer from *that* override's own real signature
   regardless of whether the original Ruby source ever defined the method
   at all — there is no "preserve the original arity for introspection"
   property worth paying bytecode for. And a real call in the narrow
   window *before* that override installs was already something this
   mechanism has to independently rule out per owner, for either design
   (see "The one real correctness question this round checked" below): if
   nothing can reach the method before the override installs, a plain
   `NoMethodError` from Ruby's own default `method_missing` covers that
   window exactly as well as an explicit `raise NotImplementedError`
   would, at zero bytecode cost — no `TDEF`/`DEF` opcode, no body opcodes,
   no new symbol-table entries at all, for any of the 17 methods.
   Re-measured for real against the identical "before" baseline this ADR
   already establishes: a real, larger recovery than design (2)'s -512
   bytes (see "The real, final numbers" below) — confirming the
   `.mrb`-file-size comparison in "Two stub designs a real measurement
   rejected" was the right early warning, not just a proxy that happened
   to agree.

Unlike `strip_wio_inline_helpers.rb`'s own hand-curated, line-text-matched
`REWRITES` table (a small, one-off substitution list authored offline
against a fixed source snapshot, per ADR 0129/0131's own history), this
script's input changes every time bc2cpp's own real coverage changes, so
the location-finding has to run for real at build time — plain `ripper`
tokens (as `strip_wio_debug_output.rb` uses) cannot give real per-node
line/COLUMN spans without re-deriving expression boundaries by hand, which
is exactly the "wrong line numbers, a `:symbol` literal confused for a
real call, multi-line call corruption" failure ADR 0129's own regex-based
first attempt documented. `RubyVM::AbstractSyntaxTree` gives those spans
directly, with real node-type checks (`CLASS`/`MODULE` nesting, `DEFN`)
rather than any text search.

Two failure modes are refused outright rather than guessed at: a one-line
`def name; body; end` (`first_lineno == last_lineno`), and a `def` whose
own signature does not fit on one physical source line (unbalanced parens
on the header line) — neither shape appears among the 17 real targets this
round strips, so both raise loudly rather than risk corrupting a shape
this script has never actually been exercised against. `.singleton`
owners (`def self.foo` / `class << self`) are never even collected as
candidates — `DEFS`/`SCLASS` span-finding needs its own, separately
verified support, deliberately out of scope here.

### Ordering: the registry never sees stripped source

The correctness constraint this whole mechanism depends on: bc2cpp's own
registry-building pass (`build_registry`, the whole-program MONO/POLY
walk) must always run against the real, unstripped source, in every gem,
every time — never the wio-stripped copy, even for a *different* class
than the one being stripped. This holds by construction, not by
convention: `wio_strip_bc2cpp_stubs` only ever reassigns
`spec.rbfiles` for the *base* gem (`mruby-rgss`) it is called from — it
never touches `mruby-rgss-compiled`'s own generation step at all. That
step's own `closed_world_srcs` (both in its real `mrbgem.rake` and in
`wio_registered_methods.rb`'s own probe run) comes from
`closed_world_mrblib_srcs`, which `Dir`-globs the base gem's real,
checked-in mrblib directory directly
(`Dir["#{gems_root}/mruby-rgss/mrblib/*.rb"]`) — never `spec.rbfiles`. So
nothing this mechanism does can reach bc2cpp's own registry input in
either direction, for any gem, at any scope. Scaling this to more owners
later does not change this property: it is a fact about how
`closed_world_mrblib_srcs` reads its input, not about which owners a given
`wio_strip_bc2cpp_stubs` call happens to name.

The wio-only guard is `spec.build.name == 'wio' && ENV['RPGMAKER_BC2CPP']`
— both, not either. Deleting a method's real `def` with no
`RPGMAKER_BC2CPP`-installed C++ override in place to replace it would be a
live correctness regression (every real call now falls through to Ruby's
own default `method_missing` and raises `NoMethodError` instead of running
real code), not just a missed flash saving, so this must never fire for a
build that does not also carry the `*-compiled` gem that makes the deleted
method's call sites unreachable in practice. The desktop/host build (used
for bc2cpp's own coverage-round work and CI) is unaffected on both counts:
`build.name` is never `'wio'` there.

### The one real correctness question this round checked rather than assumed

Constraint: could any real code path call `RGSS::Sprite`'s original Ruby
method *before* `mruby-rgss-compiled`'s own `gem_init` has run and
installed the C++ override? Gem load order is `mruby-rgss` (defines
`Sprite`, including this reopening, via its own mrblib load) then
`mruby-rgss-compiled` (`add_dependency 'mruby-rgss'` — always after) then
every other maker gem — `build_config.rb`'s own `rpg_maker_gems` calls
`conf.gem` in exactly that order, and mruby loads gems (native `gem_init`
C function, then that gem's own mrblib) strictly in dependency order. So
the only real window is *inside* `mruby-rgss`'s own native `gem_init`
(`mruby-rgss/src/lib.cxx`) — before `mruby-rgss-compiled` has even started
loading. Checked directly: grepped `lib.cxx` for any `mrb_funcall` back
into `"width"`/`"height"`/`"x"`/`"y"`/`"z"`/`"opacity"`/`"ox"`/`"oy"`/
`"zoom_x"`/`"zoom_y"`/`"angle"`/`"mirror"`/`"bush_depth"`/`"blend_type"`/
`"tone"`/`"color"`/`"src_rect"` at gem-init time. None found — every native
method definition in that file installs a C function directly; nothing
calls back into a bytecode-defined Ruby accessor during its own
construction. **No live correctness gap found for `RGSS::Sprite`
specifically.** This is not a general clearance, though: a future round
scaling this to a class whose *own* native `gem_init` genuinely calls back
into one of its own bytecode-defined methods (plausible for a class with a
native `update`/draw callback that reads a Ruby-level property) would need
to re-run this exact check for that class before stripping it — flagged
here explicitly so a future round does not skip it by analogy.

## What was measured

This ADR has now been through two real, from-scratch `pio run -e
wio_rgss_boot` A/B measurement rounds, in two separate sessions, against
two different designs of the rewrite itself: an earlier round measured the
bare-stub design (design 2 below) and reported a real **-512 byte**
flash / **zero** RAM recovery; this round re-measured from scratch, after
the rewrite's own design changed to outright `def` deletion (design 3
below), starting from a completely clean
`3rd/mruby/build/wio`/`.pio/build/wio_rgss_boot` and *not* reusing the
earlier round's own numbers or build artifacts (none remained on disk to
reuse) — the two designs' real numbers below come from two independently
provisioned builds, not one shared one. Both rounds followed the same
process: a fresh
`git submodule update --init` (`3rd/mruby`, `3rd/uni-algo`, `3rd/lvgl`,
`3rd/stb`, `3rd/mruby-marshal`, `3rd/mruby-onig-regexp`,
`3rd/mruby-stringio`, `3rd/mgem-list`), all nine `patches/*.patch` applied
by hand (`scripts/apply_mruby_patch.bash`, all applied cleanly — confirmed
idempotently, since a prior session in the same container had already
applied them once), CP932/JIS0208 tables downloaded fresh and SHA-256/SRI-
verified byte-for-byte against `flake.nix`'s own pins
(`sha256-JhTP6jXDyGxB0zGYeTqEykTt7jzw7gATphpD+6Ts4zE=` and
`sha256-HFcYcEV/Gcl3IGMfqD7kkVSalroUNtoSlnhqZ9hjLoc=`, both confirmed
byte-for-byte), `arm-none-eabi-*` 14.2.1 (PlatformIO's pinned
`toolchain-gccarmnoneeabi`, confirmed present via `arm-none-eabi-gcc
--version`), `RGSS_WIO_ARDUINO_INCLUDES` freshly extracted from a real,
non-cached `pio run -e wio -v` compile of `app/wio/src/main.cxx` (13 real
framework `-I` paths, matching ADR 0143's own count exactly), a standalone
`arm-none-eabi-g++` compile+archive of `3rd/uni-algo/src/data.cpp` with the
same trim defines `cmake/uni-algo-trim.cmake` documents, no `-flto` — the
same process ADR 0143 documents. `3rd/mruby/build/host` (the `mrbc`
bootstrap) was produced once and left in place across both builds of each
round, same as 0143 — it does not depend on this mechanism.

**`wio_registered_methods.rb` was verified against the real, live
diagnostic before anything else**: its TSV output for `mruby-rgss-compiled`
carries exactly 17 `RGSS::Sprite` entries (confirmed with a real `grep -c`
against the freshly generated `mruby-rgss-compiled_registered.tsv`),
matching ADR 0143's own independently-confirmed `register.cxx` call-site
count for this class and this gem's own documented `RGSS::Sprite` method
count exactly. The rewritten, build-time-only copy of `lib.rb` was also
read directly for this round: all 17 `def`s are gone from `class Sprite`
(surrounding comments/`attr_reader`/`attr_writer` lines untouched), the
file is 51 lines shorter than the checked-in original (17 methods × 3
lines each — a bare `def name` / body / `end`), and it still parses
(`ruby -c`) — the mechanism did exactly what it claims, not just "the
build didn't error."

### Two stub designs a real measurement rejected, before landing on deletion

Before the current delete-the-`def` design, two body-*replacing* designs
were tried and measured, in order:

1. A descriptive stub: `raise NotImplementedError, "#{self.class}#width:
   interpreted bytecode stripped for wio -- ..."`. Compiled clean, passed
   every safety check, produced a correct-looking rewrite — and the real
   link **regressed flash**: the "before" build's overflow was 1,743,484
   bytes; with that stub in place the overflow went *up* to 1,746,164
   (+2,680 bytes), not down. A string literal is never shared across
   separate compiled methods' own local `POOL` sections, even identical
   literals in different methods, so interpolating a distinct message into
   17 different method bodies costs a real, distinct string constant plus
   the `GETCONST`/string-interpolation/2-argument `Kernel#raise` opcodes in
   *each* of the 17 methods it replaces — substantially more bytecode than
   the single-ivar-read one-liner (`@x || 0`, `@bush_depth || 0`, ...) it
   was replacing.
2. A bare stub: `raise NotImplementedError` (no message) — cheaper than
   (1). This is what an earlier version of this ADR shipped with, and
   reported a real, measured **-512 byte** flash recovery / **zero** RAM
   change from a real `pio run -e wio_rgss_boot` A/B.

Real `mrbc`-compiled `.mrb` sizes for a one-method isolated test class made
the shape of the problem visible before either design was fully measured
at full link scope:

| shape | real `mrbc`-compiled `.mrb` size (no `-g`, isolated one-method test class) |
| --- | ---: |
| original one-liner (e.g. `def x; @x \|\| 0; end`) | 161 bytes |
| bare `raise NotImplementedError` | 184 bytes |
| `raise NotImplementedError, "#{self.class}#x: ...interpolated message..."` | 406 bytes (with `-g`; the real linked delta across all 17 methods was +2,680 bytes) |

**A later, independent host-side check went one step further and falsified
design (2)'s own -512 byte number as a general expectation, before this
round's real re-link confirmed why**: `mrbc`-compiling the *whole* real
`mruby-rgss/mrblib/lib.rb` (not an isolated one-method fixture) with the
bare-stub rewrite actually applied came out *larger* than the untouched
original — +153 bytes without `-g`, +122 bytes with `-g` (the flag the
real wio build's own `enable_debug` adds to `mrbc`) — apparently
contradicting design (2)'s own reported real link delta. The reconciling
explanation, confirmed directly: `NotImplementedError` does not appear
anywhere else in `lib.rb`, so the stub's own `raise NotImplementedError`
introduces a **new symbol-table entry** (`NotImplementedError` itself, on
top of `raise`) that every one of the 17 stubbed methods now references —
a real, whole-file-scoped cost (mruby's per-`.mrb` symbol table is
deduplicated once per file, not per method) that an isolated one-method
`.mrb` fixture like the table above cannot see at all, since with only one
stubbed method in the fixture there is only one method paying for that new
symbol table entry either way. At whole-file scope with 17 real stubbed
methods sharing one symbol table, the *marginal* first-time cost of adding
`NotImplementedError` to that table plus 17x the `SSEND`/`GETCONST`-family
opcodes needed to reference it outweighed the 17x savings from dropping
each method's own now-unused ivar symbol (`@x`, `@bush_depth`, ...) — even
though the whole-file real *link* still came out net-negative overall
(other, non-`RGSS::Sprite` interactions at final link — `--gc-sections`,
`-fmerge-all-constants` — evidently still recovered slightly more than
this file-level regression cost). This is exactly the shape of gap this
whole ADR series exists to catch: a real, whole-program `pio run` link and
an isolated per-method proxy measurement can disagree about a *design's*
sign even when both are individually real and correctly measured, because
they are measuring costs at different, non-commensurable scopes (a
whole-file/whole-link shared symbol table vs. a single isolated method).

**This directly motivated design (3), the one that actually ships**:
delete the whole `def` — header, body, and `end` — rather than replacing
it with anything. See "The two new pieces" above for the correctness
argument (nothing can call the method before the real C++ override
installs, the same property either stub design already had to establish
per owner) and `strip_wio_bc2cpp_stubs.rb`'s own file comment for the full
reasoning. A same-day, whole-file `mrbc` re-check of this exact concern —
run before the real link below, to make sure design (3) does not repeat
design (2)'s own "isolated fixture says smaller, whole file says bigger"
surprise — confirmed it does not:

| shape (whole real `mruby-rgss/mrblib/lib.rb`, all 17 `RGSS::Sprite` methods rewritten) | `mrbc`-compiled `.mrb` size, no `-g` | with `-g` (real wio flag) |
| --- | ---: | ---: |
| original, unmodified | 28,506 | 33,694 |
| bare `raise NotImplementedError` stub (design 2) | 28,659 (**+153**) | 33,816 (**+122**) |
| whole `def` deleted (design 3, shipped) | 27,360 (**-1,146**) | 32,108 (**-1,586**) |

Design (3) is unambiguously smaller than *both* the original and design
(2), at whole-file scope, with or without `-g` — no new symbol-table entry
of any kind, since nothing referencing `NotImplementedError` is ever
written. This is a strong, whole-file, real-`mrbc` signal that design (3)
should out-perform design (2)'s real, linked -512 bytes — but per this
series' own repeated lesson just above (a whole-file `.mrb` size is still
not the real, whole-*program*, linked, `--gc-sections`-and-`-fmerge-all-
constants`-affected number), that still had to be confirmed with a real
link rather than trusted on its own, which is what follows.

### The real, final numbers

Both `RPGMAKER_BC2CPP=1` builds carry the identical, full ~31-round
coverage scope (`mruby-lcf-compiled`/`mruby-rgss-compiled`/
`mruby-rpg2k-compiled`, 1,573 methods total, unchanged by this ADR) — the
ONLY difference between them is whether `wio_strip_bc2cpp_stubs` actually
ran for `mruby-rgss`'s own wio build (commented out for "before", active
for "after", using the current, shipped, delete-the-`def` version of
`strip_wio_bc2cpp_stubs.rb`), isolating this mechanism's own effect as a
clean, single-variable A/B within the same session/toolchain. Confirmed
directly, not just assumed from the diff: the "before" build's own rake log
never mentions `wio_bc2cpp_stubbed` at all (the mechanism did not run), the
"after" build's does, and its own generated TSV/rewritten `lib.rb` were
read directly and checked as described above.

| | before (BC2CPP=1, no stripping) | after (BC2CPP=1, RGSS::Sprite `def`s deleted) | delta |
| --- | ---: | ---: | ---: |
| `.text` (flash) | 2,211,504 | 2,210,808 | **-696** |
| `.ARM.extab` | 4,556 | 4,556 | 0 |
| `.ARM.exidx` | 35,240 | 35,240 | 0 |
| `.data` (RAM) | 12,880 | 12,816 | **-64** |
| `.bss` (RAM) | 19,360 | 19,360 | 0 |
| **Flash needed** (`.text`+`.ARM.extab`+`.ARM.exidx`) | **2,251,300** | **2,250,604** | **-696** |
| **RAM used** (`.data`+`.bss`) | **32,240** | **32,176** | **-64** |
| real `ld` "region FLASH overflowed by" | 1,743,396 | 1,742,700 | **-696** |

**Sanity check against docs/adr/0143's own recorded full-scope baseline**
(`.text` 2,211,592, flash needed 2,251,388, overflow 1,743,484): this
session's own "before" number is extremely close but not bit-exact — every
field matches exactly (`.ARM.extab`, `.ARM.exidx`, `.data`, `.bss`, and
therefore RAM used) except `.text`/flash-needed/overflow, each off by
**exactly -88 bytes** in the same direction. Investigated rather than
waved off: a standalone rebuild of `3rd/uni-algo/src/data.cpp` with the
documented trim defines in this session came out 44-48 bytes *larger* than
ADR 0140/0143's own recorded 145,440 (145,484 without
`-ffunction-sections`/`-fdata-sections`, 145,488 with) — the wrong sign and
roughly half the magnitude to fully explain -88 bytes on its own, so it is
at most a partial contributor. The remainder is most plausibly ordinary
toolchain/link-environment noise this project's own history already
documents as real (ADR 0130's own proxy-vs-real-link numbers landed
"within about 5%... never expected to match exactly" for the same reason:
linker padding, alignment and `--gc-sections`/relaxation decisions are not
perfectly reproducible byte-for-byte across independently-provisioned
toolchain installs, only close). At 0.004% of the real `.text` size and
identical across every other field, this is treated as acceptable
reproduction, not a scope error — the kind of small, unreconciled gap this
ADR series has already precedented (0143's own gross-vs-net per-symbol
gaps) — and specifically does **not** undermine the "after" delta, which
is measured against this session's *own* "before" in the same environment,
not against 0143's numbers directly.

**A real, larger, fully-verified recovery than either stub design**: 696
bytes of flash, *and*, unlike both stub designs (and unlike this whole
series' own consistent "RAM is always bit-for-bit identical" finding since
ADR 0142), a real 64-byte RAM (`.data`) reduction. The RAM change is a
genuinely new finding this round surfaces that neither prior round did:
deleting the `def`s outright removes 17 methods' worth of entries from
`mruby-rgss`'s own compiled mrblib `irep` (symbol names, local-variable
metadata, and any small per-method bookkeeping table `mrbc`'s C dump
emits) rather than merely replacing their bodies, and evidently at least
one such table lands in an initialized, non-`const` global (hence `.data`,
not `.rodata`) in the generated `gem_init.c` for this gem — plausible, and
directionally consistent with 51 fewer physical source lines producing a
smaller generated table, but not traced to one specific symbol via
`arm-none-eabi-nm` in this round (a real, scoped, honestly-flagged gap for
a future round to close if the RAM axis becomes a priority, not asserted
here as more precisely understood than it is).

696 bytes is still small in absolute terms against docs/adr/0143's
1,067,524-byte full-scope regression — `RGSS::Sprite`'s own 17 methods are
all trivial single-ivar-read accessors, already near `mrbc`'s own
per-method bytecode floor, so there was never much to recover from this
specific class (unlike, say, `Game::Battle`'s real damage-formula methods
or `Game::Party`'s equip/skill logic, which are `mruby-rpg2k-compiled`'s
own dominant flash cost per docs/adr/0143 and would very plausibly show a
larger recovery each). What matters for this round's own goal is that the
number is *real, positive, and now the largest of the three real
end-to-end measurements this ADR has produced* — the mechanism, in its
current delete-the-`def` form, does more of what it is supposed to do than
either earlier stub design, confirmed through the same real linker map
every other ADR in this series trusts, not extrapolated from the `.mrb`-
size comparisons above (which predicted the right *direction* and
*ranking* of all three designs, but not the exact linked magnitude —
consistent with this whole section's own repeated finding that a
pre-link, per-file or per-method proxy and the real, whole-program,
`--gc-sections`-affected link are related but not numerically
interchangeable).

Neither build links or boots — both are still far over the real
507,904-byte flash budget (same pre-existing, unresolved overflow docs/adr
0104-0143 already established); this is a controlled A/B on top of that
shared, still-unfit baseline, same as every bc2cpp measurement ADR before
it.

## Consequences

- **A real, generalized, wio-only bytecode-stripping mechanism now exists**
  and is proven correct end to end on a real, bounded class: real
  `bc2cpp.rb` diagnostic capture (no re-derivation), a real AST-based
  rewrite (verified against the actual `mruby-rgss/mrblib/lib.rb`, not a
  synthetic fixture), a real clean recompile, and a real, measured flash
  delta on the real `wio_rgss_boot` target.
- **The real, measured recovery for this round's bounded scope is small: 696
  bytes of flash, 64 bytes of RAM**, against docs/adr/0143's own
  +1,067,524-byte flash / +0-byte RAM full-scope regression — a real,
  positive, fully-verified data point (superseding this ADR's own earlier
  -512-byte/0-RAM number, measured against an earlier, body-replacing stub
  design since replaced by outright `def` deletion — see "What was
  measured" for the full history of both designs and why the later one
  wins), not yet a meaningful dent in that number. Confirms the mechanism
  is sound and worth having, but also confirms it needs to reach far more
  (and, on average, larger and more formula-heavy) methods than 17 trivial
  accessors before it changes the bottom line docs/adr/0143 already
  established.
- **Scaling this to more owners is real, tracked follow-up work, not
  attempted in this round.** Two things would need to happen first for
  each additional owner: (1) the same gem-init-ordering correctness check
  this ADR did for `RGSS::Sprite` (native code that calls back into its
  own bytecode-defined methods during its own `gem_init` is a real,
  class-specific risk, not something this mechanism can rule out in
  general), and (2) real coverage of the two deliberately-unsupported
  shapes (`.singleton` owners, one-line `def`s / multi-line signatures) if
  the next owner's methods need either — most of `mruby-rpg2k-compiled`'s
  own 1,457 methods, the dominant share of bc2cpp's real flash cost per
  ADR 0143, live on classes with real `.singleton` owners and non-trivial
  method bodies, so a meaningful further recovery pass needs that
  follow-up work done first, not just a longer `owners:` list on this same
  call.
- The desktop/host build is unaffected: `wio_strip_bc2cpp_stubs` is a
  no-op unless `spec.build.name == 'wio'`, same convention as
  `wio_strip_debug_rbfiles`/`wio_strip_inline_helpers` before it.

## What was not done

- Scaling beyond `RGSS::Sprite` — deliberate, per this ADR series'
  "bounded subset first" discipline; see Consequences above for exactly
  what a future round needs to check per additional owner before doing so.
- `.singleton` (DEFS/SCLASS) support in `strip_wio_bc2cpp_stubs.rb` — real,
  scoped-out follow-up; needed before this mechanism can reach the 31
  `.singleton` owners already covered by `mruby-rpg2k-compiled`/
  `mruby-rgss-compiled` today.
- Multi-line `def` signature and one-line `def name; body; end` support —
  neither shape was needed for this round's 17 targets; both raise loudly
  rather than silently mishandle a method shape this script has never been
  exercised against.
- Re-deriving whether `RPGMAKER_BC2CPP=1` is worth shipping for wio at all
  even after this recovery — docs/adr/0143's own bottom line (a huge net
  flash regression at full scope) is unaffected by anything in this ADR;
  this mechanism narrows the gap, it does not close it, and closing it
  fully would need every owner covered, both `.singleton` support and the
  gem-init-ordering check done per class, and even then the fixed
  per-gem overhead ADR 0143 found (most of the real cost, independent of
  method count) may not be recoverable by this mechanism at all.
- Tracing the real, measured 64-byte RAM (`.data`) reduction to one
  specific symbol via `arm-none-eabi-nm` on `mruby-rgss`'s own generated
  `gem_init.o` — a plausible mechanism is given in "What was measured"
  (fewer methods' worth of per-method bookkeeping in the compiled `irep`),
  but this round did not save both builds' own `gem_init.o` to diff them
  directly, so the explanation is honestly flagged as plausible-but-
  unconfirmed rather than fully traced.

## Follow-up: `.singleton` (DEFS/SCLASS) support, and scaling to `RGSS::Window`/`RGSS::Audio.singleton`/`RGSS::ErrorReport.singleton`

Date: 2026-09-12

Closes the two gaps the "What was not done" section above named as
blocking this mechanism from reaching more of bc2cpp's own real coverage:
`.singleton` (DEFS/SCLASS) support in `strip_wio_bc2cpp_stubs.rb`, and the
per-owner gem-init-ordering correctness check for owners beyond
`RGSS::Sprite`. Per this ADR series' own "prove it, then scale it in a
bounded, re-checked step" discipline (the same one 0139 itself used
across ~31 rounds), this scales to three more owners **already covered by
`mruby-rgss-compiled`'s own real `owners:` list**
(`tools/bc2cpp/compiled_gems.rb`) — bc2cpp's own AOT coverage itself is
unchanged by this round, only how much of bc2cpp's *existing* coverage
this stripping mechanism can now reach.

### `.singleton` support in `strip_wio_bc2cpp_stubs.rb`

`collect_defs` now also collects two more real AST node shapes, matching
bc2cpp.rb's own `build_registry`/`resolve_singleton_receiver` "owner
string ends in `.singleton`" pseudo-owner convention exactly (confirmed by
reading that function directly, not assumed by analogy):

- **`DEFS`** (`def self.foo` at a class/module body's own top level) — a
  new `self_receiver?` helper checks the node's own receiver child against
  the real `:SELF` AST node type (confirmed via a live
  `RubyVM::AbstractSyntaxTree.parse` dump — see below) before recording it
  under `"#{enclosing_path}.singleton"`; a non-`self` receiver (`def
  SomeOtherConst.foo`, a real, different DEFS shape with a `CONST`/`COLON2`
  receiver node) is never collected as a candidate at all, regardless of
  what a hand-built TSV might claim about it.
- **`SCLASS`** (`class << self; ...; end`) — same `self_receiver?` gate on
  the SCLASS's own receiver; when it passes, the body is walked with a
  `singleton_owner` override so every ordinary `DEFN` found inside it
  (`def bar; ...; end`, no `self.` prefix — SCLASS puts the *class itself*
  in the singleton context, so methods defined inside it need no `self.`
  marker of their own) is recorded under that same `.singleton` owner
  string instead of the enclosing non-singleton `stack`. A `class <<
  SomeOtherReceiver` (non-`self`) is left completely untouched, same as a
  non-`self` DEFS.

Real line-span behavior was checked directly against a live AST dump
before trusting it (`ruby -e 'RubyVM::AbstractSyntaxTree.parse(...)'` on a
small fixture with both shapes), not assumed to match plain `DEFN`'s:

```
DEFS 3-5 children_types=[:SELF, ":setup_midi", :SCOPE]     # def self.setup_midi / body / end
SCLASS 7-11 children_types=[:SELF, :SCOPE]
  DEFN 8-10 children_types=[":bgm_stop", :SCOPE]           # def bgm_stop / body / end, nested inside
```

Both `DEFS` and an `SCLASS`-nested `DEFN` use the *exact* same
`first_lineno`/`last_lineno` convention a plain instance-method `DEFN`
already does — the header's own line through the matching `end`'s own
line, with the `class << self ... end` wrapper's own (wider) span never
touched. No quirk was found that `apply_deletion_plan` needed any change
for — it works on both new shapes completely unmodified. `load_registered`
no longer blanket-drops every `singleton == '1'` TSV row; instead it
raises loudly if a `.singleton`-suffixed owner string and the TSV's own
`singleton` column ever disagree, as a defense against
`wio_registered_methods.rb`'s own TSV shape drifting silently out from
under this file's own assumption of what "singleton" means.

**Verified in isolation before touching any real project file**, the same
way the original design was: a hand-written fixture
(`module RGSS; module Widget; def self.foo(a, b = 1); ...; end; class <<
self; def bar; ...; end; end; class Other; end; def Other.foo; ...; end;
end; end`, plus an unrelated `class Plain; def x; ...; end; def y; ...;
end; end`) with a hand-built TSV naming `RGSS::Widget.singleton#foo`,
`RGSS::Widget.singleton#bar`, `RGSS::Widget::Other.singleton#foo` (a
trap — this owner is *never* collected as a candidate no matter what the
TSV says, because `Other.foo`'s own receiver is the real constant `Other`,
not `self`), and `RGSS::Plain#x`. Running the real, updated script against
it and reading the output directly confirmed: `foo` (DEFS) and `bar`
(SCLASS-nested DEFN) both gone, `kept_defs`/`kept_sclass` (unregistered)
both still present, `Other.foo` untouched (proving the `self`-receiver
gate actually holds even when the TSV names a matching owner), `Plain#x`
gone and `Plain#y` (unregistered) untouched, and the whole rewritten file
still parses (`ruby -c`: `Syntax OK`). A second isolation check confirmed
`load_registered`'s new consistency guard actually fires: a TSV row
claiming owner `RGSS::Widget.singleton` with its own `singleton` column
set to `0` raised immediately, before any file was ever rewritten.

### The gem-init-ordering correctness check, re-run per owner (not assumed by analogy)

Same check ADR 0144's original round did for `RGSS::Sprite`: could any of
`mruby-rgss`'s own native source call back into one of these methods'
*Ruby* definitions before `mruby-rgss-compiled`'s own `gem_init` installs
the real C++ override? Grepped every file in `mruby-rgss/src/*.cxx` (all
15 of them, not just `lib.cxx` and not just inside `gem_init` itself — a
wider net than the original round's own check) for a real `mrb_funcall`
back into any of the 31 target method names:

- **`RGSS::Window`**'s 12 names (`opacity`, `cursor_rect`, `active`,
  `pause`, `back_opacity`, `stretch`, `openness`, `open?`, `close?`,
  `padding`, `padding_bottom`, `arrows_visible`): zero matches anywhere.
- **`RGSS::Audio.singleton`**'s 13 names: zero matches in `audio.cxx`
  (`rgss_audio_define`, the file's own native init function, defines only
  underscore-prefixed native primitives — `_bgm_volume`, `_bgm_pan`, ... —
  which the bytecode-defined, non-underscore wrapper methods this round
  strips call *into*, never the reverse) or anywhere else in the gem.
- **`RGSS::ErrorReport.singleton`**'s 6 names: zero matches. `lib.cxx`
  does reference `RGSS::ErrorReport` by name (a comment, and
  `RGSS.__log_bridge_write` — a native method `ErrorReport.push` itself
  calls *into*, again the opposite direction), but nothing calls back into
  `push`/`installed?`/`record`/`clear`/`probe!`/`probe_raise` from native
  code at all.

**No live correctness gap found for any of the three**, confirmed
directly rather than assumed from `RGSS::Sprite`'s own prior clean result.

**A real, honestly-flagged aside, found by casting this wider net (not
this round's own concern, since neither owner was chosen this round, but
worth recording rather than silently noticing and dropping)**: two calls
back into *other* real `.singleton` owners' own bytecode methods do exist
in this gem's native code —
`RGSS_warn_stub` (`lib.cxx`) does `mrb_funcall(..., "warn_stub", ...)`
into `RGSS.singleton`, called from several native methods whenever a game
exercises an unimplemented native code path; and `wio_input_bridge.cxx`'s
own `send_key` does `mrb_funcall(..., "press"/"release", ...)` into
`RGSS::Input.singleton`, called from `rgss_wio_poll` once per frame via
`Graphics.update`. Both are real *runtime* call paths (long after every
gem's own `gem_init` has finished), not gem-init-time ones, so neither
looks like it would actually block stripping `RGSS.singleton` or
`RGSS::Input.singleton` in a future round — but this round did not stop to
fully confirm that the way it did for its own three chosen owners, so a
future round scaling to either must still re-run this exact check itself
rather than cite this paragraph as clearance.

originally shipped) and "after" (this round's own four-owner

~31-round/1,573-method coverage scope, unchanged by this round. `.text`/
`.data`/`.bss`/`.ARM.extab`/`.ARM.exidx` read directly from the real `ld`

(its "after" number for `RGSS::Sprite` alone: `.text` 2,210,808, flash
needed 2,250,604, RAM used 32,176): this round's own from-scratch "before"

comes in at `.text` 2,212,072 — **+1,264 bytes** (0.057%) — with `.data`
+16 bytes and `.ARM.extab`/`.ARM.exidx`/`.bss` bit-for-bit identical. Not

the prior round's numbers directly.

average recovery here (~71.5 bytes/method) is meaningfully larger than
`RGSS::Sprite`'s own (~40.9 bytes/method) — consistent with this ADR's own
prediction that `RGSS::Sprite`'s trivial single-ivar-read accessors were
close to `mrbc`'s per-method floor already, while `RGSS::Audio.singleton`'s
methods (each takes real arguments and does real work: volume/pan
clamping, a native `_bgm_fade`/`_bgm_stop` dispatch) had more bytecode to
actually remove.
