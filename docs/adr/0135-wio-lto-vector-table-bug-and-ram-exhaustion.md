# 135. Revert -flto (a real boot-breaking bug), and a real RAM-exhaustion crash found once the fix let wio_rgss_boot actually run

Date: 2026-09-10

## Status

Accepted

## Context

Asked to widen `wio_rgss_boot`'s flash budget for a diagnostic run and dump
the live mruby VM state right after init under this project's own Renode
emulator (docs/adr/0094), the very first boot attempt aborted immediately:
a wild jump to `0xD0024282` moments after reset, on the *real*, currently
committed `env:wio` and `env:wio_rgss_boot` (not just the widened diagnostic
build) -- the actual point of this ADR moved before the original heap-dump
question could even be reached.

### Part 1: -flto strips the ARM vector table

Bisected by building `env:wio` with each of ADR 133's three flags in
isolation: GCC 14.2.1 alone boots fine under Renode; `-fmerge-all-constants`
alone boots fine; **`-flto` alone reproduces the identical abort.**

Root cause, confirmed by reading the linked ELF directly (`objdump`/`nm`):
with `-flto`, the `.isr_vector` section -- the ARM Cortex-M reset/interrupt
vector table a real chip reads at a fixed address to get its initial stack
pointer and `Reset_Handler` address -- is **entirely absent from the
binary**. Without `-flto` it sits correctly at `0x4000` (`SP=0x20030000`,
`PC=Reset_Handler`); with `-flto`, that same address holds unrelated
inlined code, and no `.isr_vector` section exists anywhere in the ELF.
PlatformIO's vendored Arduino/SAMD startup code (`cortex_handlers.c`, not
owned by this project) places that array only via the linker script's own
`KEEP(*(.isr_vector))` -- it is never reached by a real call-graph edge, and
is not marked `__attribute__((used))`. That is exactly the shape LTO's own
whole-program dead-code elimination (which runs *before* the final link,
earlier than `KEEP()`/`--gc-sections` ever get a say) is liable to discard
outright, compiling it out of the object entirely rather than merely
misplacing it.

**Not a Renode-only artifact.** A real SAMD51 boots by reading the same
fixed vector-table address, so `env:wio`/`env:wio_rgss_boot` as configured
by ADR 133 would very likely have failed to boot on real hardware too,
despite linking cleanly and reporting a correctly-sized image. ADR 133 was
verified only by linker output size and CI compile success -- never
actually run, on hardware or under emulation.

### Part 2: a second, unrelated, more fundamental bug -- surfaced only once Part 1 was fixed

With the vector table restored, `wio_rgss_boot_main.cxx`'s `setup()` now
runs for real under Renode: `wio_display_create()`, `wio_input_init()`,
`mrb_open_core()`, and `rpg_maker_init_shared_gems()` all succeed. It then
crashes inside `rpg_maker_init_rpg2k_gem()`, part way through executing the
`mruby-rpg2k` gem's own generated bytecode
(`GENERATED_TMP_mrb_mruby_rpg2k_gem_init` -> `mrb_load_proc` ->
`mrb_vm_exec`), while defining one more method on a class
(`mrb_define_method_raw` -> `mt_grow` -> `mrb_realloc`, requesting 384
bytes). That `mrb_realloc` fails, raises `NoMemoryError`, which -- since
this build carries real C++ exceptions (mruby-rgss/mruby-lcf/mruby-marshal
all have `.cxx` sources, see docs/adr/0134) -- goes uncaught, reaches
`std::terminate()`, and calls `abort()`.

Confirmed via GDB attached to the running emulator (breakpoint on `abort`,
inspecting `new.cpp`'s `_sbrk()` internal `heap_end` static and the current
stack pointer directly): at the moment of failure, `heap_end` sat only
**100 bytes** below the current stack pointer -- `_sbrk`'s own safety check
(`old_end + incr >= (char*)__get_MSP()`) is exactly what rejected the
384-byte request. The heap had already grown **162,556 bytes** past
`__end__` (the end of `.data`/`.bss`) by that point. Out of a 196,608-byte
total RAM budget, essentially all of it was gone: `.data`/`.bss` (~33 KB) +
heap growth (162,556 bytes) + stack depth so far (704 bytes) leaves only
that 100-byte gap.

This is a genuinely separate bug from Part 1, with its own consequence:
**even once `wio_rgss_boot` someday fits in flash, it will not finish
booting on real hardware as currently written** -- it exhausts the entire
RAM budget partway through loading the `mruby-rpg2k` gem's own class/method
definitions, before user Ruby code, before `mrb_full_gc(M)`, before
anything resembling steady-state runtime state ever exists. The original
ask -- dump the live VM state right after init to see what is worth
trimming -- cannot be answered as asked, because init does not complete.
The more useful answer it surfaced instead: **defining the RGSS/mruby-lcf/
mruby-rpg2k class and method tables alone, as live heap objects, costs on
the order of 160+ KB of RAM** (this total includes whatever LVGL's own
earlier display-buffer allocations already took from the same shared heap,
per docs/adr/0112 -- not isolated to mruby's own share, since no baseline
sample was taken between `wio_display_create()` and `mrb_open_core()`).
That single number dwarfs every per-method/per-feature trim this whole
series has made combined, and reframes what "shrinking wio" actually needs:
not fewer RGSS methods inlined away, but keeping the *compiled program
structure itself* -- classes, methods, symbol tables -- out of live RAM in
the first place. This is the same conclusion every ADR in this series has
already landed on for flash (ADR 108's unfinished SD-external-bytecode
loader), now shown to apply just as hard, maybe harder, to RAM.

## Decision

**Revert `-flto`.** Removed from `platformio.ini` (`env:wio`,
`env:wio_rgss_boot`) and from `build_config.rb`'s wio cross-build flags;
`conf.archiver.command` reverted from `arm-none-eabi-gcc-ar` back to plain
`arm-none-eabi-ar` (no longer archiving LTO IR objects). `-fno-ident` and
`-fmerge-all-constants` stay -- each independently confirmed, by itself, to
boot correctly under Renode with the vector table intact. The GCC 14.2.1
toolchain upgrade (`platform_packages`) also stays, for the same reason:
confirmed independently to boot correctly, and real bytes still come from
it (newer `-Os` heuristics) plus `-fmerge-all-constants`, even without
`-flto`.

**Keep, and commit, the diagnostic infrastructure that found both bugs**
(docs/adr/0094's Renode platform made this possible at all): a new
PlatformIO environment, `wio_rgss_boot_heapdbg` (`platformio.ini`), pairing
a widened throwaway linker script (`app/wio/renode/
oversized_flash_debug.ld`, FLASH widened to 2 MB, never a real hardware
config) with a matching widened Renode platform description
(`app/wio/renode/wio_terminal_oversized_flash.repl`, `flash0` widened to
match) and `-g` for DWARF type info -- letting a build that currently
overflows real flash still link, load, and be inspected live via GDB
attached to Renode's GDB server. Not wired into a default `pio run` or CI,
same convention as `wio_mruby_sd_smoke`.

**Did not attempt a RAM fix in this ADR.** Fixing the exhaustion needs
either genuinely reducing how much class/method structure this build
builds (further gem/feature trims, on top of everything ADR 129-132
already did), or not building it as live heap state at all (a bytecode
representation that does not require constructing full `RClass`/method-
table objects for everything up front) -- both larger, separate efforts
than this ADR's own scope.

## What was verified

A full clean rebuild of `libmruby.a` (wio target, real C++ exceptions,
`RGSS_WIO_ARDUINO_INCLUDES`, no `-flto`) and a standalone `uni-algo`
cross-build with matching flags, then a real `pio run -e wio_rgss_boot`
link from a clean `.pio/build/wio_rgss_boot`:

```
before (ADR 132, GCC 7.2.1, no LTO):                region `FLASH' overflowed by 842344 bytes
ADR 133 (GCC 14.2.1 + -flto, later found to not boot): region `FLASH' overflowed by 651824 bytes
after   (GCC 14.2.1, -flto reverted):                region `FLASH' overflowed by 684080 bytes
```

**A real, corrected 158,264-byte reduction from the toolchain upgrade and
the two surviving flags** -- smaller than ADR 133's originally claimed
190,520 bytes, but real and (as far as flash size alone can attest to)
bootable, unlike ADR 133's own number.

Booted the corrected, real (non-widened-flash-diagnostic) build's own code
under Renode via `wio_rgss_boot_heapdbg`: confirmed via GDB that `PC` at
reset now correctly lands on `Reset_Handler` in `cortex_handlers.c` (not a
wild jump), that `wio_display_create`/`wio_input_init`/`mrb_open_core`/
`rpg_maker_init_shared_gems` all complete, and that the RAM-exhaustion
abort inside `rpg_maker_init_rpg2k_gem` is itself real and reproducible
(two independent clean-boot runs, same failure, same `mrb_realloc` call
site and same ~100-byte final margin).

`env:wio` (the actual bring-up firmware, no mruby) was also rebuilt and
re-verified booting cleanly under Renode with `-flto` gone.

## Consequences

- **ADR 133's flash-reduction claim was wrong**, not just imprecise: the
  firmware it shipped would not have booted. This ADR's corrected number
  (158,264 bytes, not 190,520) is what should be cited going forward; ADR
  133 itself is left as-written (historical record) but is superseded by
  this one for the `-flto` decision specifically.
- **A firmware that links, fits, and reports a plausible size is not
  evidence it runs.** Every prior ADR in this series relying solely on
  linker/`pio run` output (which is most of them) implicitly assumed this;
  it is not a safe assumption for flag changes that touch codegen this
  deeply, and this project had no boot-level regression check in CI before
  this ADR.
- **wio_rgss_boot has a second, independent blocker beyond flash size**:
  RAM exhaustion during gem init. Even a hypothetical future change that
  got flash under 507,904 bytes would still not produce a working boot
  without also addressing this. This changes the priority ordering for any
  future wio shrink work -- RAM, not just flash, is now a confirmed hard
  blocker, not a theoretical one.
- `wio_rgss_boot_heapdbg` plus its two new committed assets are now a
  reusable tool for any future "does this actually boot, and what does it
  look like right before it dies" investigation on this target, without
  needing to re-derive the widened-flash-region trick from scratch.
